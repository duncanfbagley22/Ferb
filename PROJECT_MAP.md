## Overview
- **Project Type**: Native iOS app, SwiftUI + SwiftData (iOS 17+)
- **Purpose**: Personal health/habit tracker organized into four fixed areas (Surface, Structure, Internal, Regulation) and 34 built-in subareas (more can be added). **Items** are definitions of things that can be measured; **Targets** are what you act on (cadence, start date, window, goal value, tolerance). **Logs** record completions, with a value for measured items.
- **Tech Stack**: Swift, SwiftUI, SwiftData (local on-device storage, no backend, no sync, no export yet), UserNotifications (local alerts only), EventKit (read-only calendar events), ActivityKit + WidgetKit (timer Live Activity)

## Key Files
- **FerbApp.swift**: `Schema([Item, Subarea, Target, Log, Note, Reminder, CustomUnit, PlanEntry])` (a comment there says: a new model must also be added to `deleteAllData()` in `SettingsView`), on-disk container, the light/dark override stored with `@AppStorage("appearance")`, and in `init()` it sets `NotificationRouter.shared` as the notification delegate (early, so a tap that launches the app is delivered).
- **TargetPeriods.swift**: the single source of truth for done/missed. Status, card dots, Quick update and the Calendar all read from it.
- **TargetQuickLog.swift**: `needsQuickLog()` is the single definition of "this target still needs logging today" (active, not snoozed, current period not met, not a cap, not NFC; a time target with a logged time in its current period is not offered again, even if the log missed its window). The evening alert and plan alerts use it. Quick update uses `needsQuickUpdate()`, the same except caps are included (a cap is offered once a day until something is logged for it that day, or it's set aside); caps stay out of `needsQuickLog` so the evening alert doesn't fire for a cap that stays open all day.
- **TargetLogInput.swift**: shared by Quick update and Log now. `Target.logInputKind` (check / amount / duration / durationTimer / time), `LogDraft` (typed number and time, plus `resolve(target)` giving the value to log or a warning), `TargetLogInputs` (the input view, with ± arrows on number fields stepping 1/10/100 by goal size; amount, duration and timer cards also show an `AmountDial` above the field, which writes the snapped amount to `draft.numberText`; the check card is a `HoldToCompleteCheck` that calls the optional `onComplete` closure, which Quick update sets to `commitRight` and Log now to `save`), and timer helpers on `Target` (`timerSeconds`, `toggleTimer`, `clearTimer`), plus `loggedSoFarText`. `toggleTimer` and `clearTimer` also start / pause / end the Live Activity (via `TimerActivity`), so every logging path stays in step without extra calls.
- **Log.swift**: log creation and deletion should always go through `target.record(...)` / `target.remove(...)`.

## Data Layer
- `Area` (enum): `.surface` (A), `.structure` (B), `.internals` (C, displays "Internal"), `.regulation` (D). Exposes `letter` and `title`.
- `Subarea` (`@Model`): `key` (stable id; built-ins use the old enum names like "hair", custom ones a UUID), `title`, `area`, `isBuiltIn`, `sortOrder`, `items`. 34 built-ins are seeded by `Subarea.seedDefaults` (adds only missing ones) when `ContentView` appears. Custom ones can be added from the item form and renamed/deleted in Settings → Subareas (deletion only if no item uses it; built-ins can't be deleted).
- `Item` (`@Model`): `name`, `subarea?`, `createdAt`, tracking fields (`trackingType`, `binarySubtype?`, `quantitySubtype?`, `quantityDirection?`, `unit?`), `isPriority`, `isArchived`, `method: TrackingMethod?`, `customUnit?` (a user-added unit, used instead of `unit`, never both), `targets` (cascade), `planEntries` (cascade). Computed: `area` (optional, from the subarea), `unitName` (the unit text every screen shows next to numbers), `effectiveMethod` (stored method, else binary -> check, duration -> timer, other quantity -> number). Today the method only matters for the timer card and for NFC items being left out of Quick update (they're logged manually through Log now until real NFC exists).
- `Target` (`@Model`): `item?`, `startDate`, `durationDays?` (nil = ongoing), `intervalDays`, `value?` (goal, or minutes since midnight for time targets), `tolerance?`, `toleranceMode`, `timeDirectionStored?` (with a computed `timeDirection` that defaults to `.either`; stored as optional so old rows with no value don't crash), `reward?` (unused), `isArchived`, `timerStartedAt?` / `timerAccumulated` (saved timer; survives leaving the screen or closing the app), `snoozedUntil?` (set by Quick update's "Not today" to the start of tomorrow; while in the future `needsQuickLog()` is false, so the alerts follow; cleared by Restore or Undo), `skippedOn?: [Date]` (days a period was skipped with X in Quick update; see Status and Period Logic), `showFromMinutes?: Int` (minutes since midnight; while the clock is before it, the target stays out of Quick update and its Home tile is blue, via `isBeforeShowTime()` in `TargetQuickLog.swift`; nil = always shown; set in the target form's Quick update section, editable even with logs), `isRolling?: Bool` (true = rolling window, see Status and Period Logic; nil/false = fixed blocks), `badgeNudge?: Bool` (true = counts toward the app icon's red badge each day until logged, skipped or set aside; see Alerts), `logs` (cascade). Computed: `area`, `cadenceTitle`, `lastCompletedAt`, `endDate()`, `isHidden` (archived, or its item is), `isActive(asOf:)` (false when hidden), `dateRangeText`. Creating a new target trims the item's earlier running targets to end the day before.
- `Log` (`@Model`): `target?`, `completedAt`, `value: Double?`. `Target.record(value:at:in:)` creates, attaches to `target.logs` immediately, and saves (so colors update at once); `Target.remove(_:in:)` is the inverse.
- `Note` (`@Model`): `body`, `createdAt`, `updatedAt`; first line is the title.
- `CustomUnit` (`@Model`): `name`, `createdAt`, `items` (nullify). Added from the item form ("New unit…"); renamed or deleted in Settings → Units (deletion blocked while any item, archived ones included, uses it). A name matching a built-in or existing unit selects that one instead of duplicating.
- `PlanEntry` (`@Model`): `weekday` (1 = Sunday), `startMinutes`, `durationMinutes`, `item?` (cascade from `Item.planEntries`), `createdAt`, `date?`. No `date` = weekly slot repeating on that weekday; with a `date` (start of day) = one-off slot shown only that day (`weekday` is then that date's weekday). `endMinutes` is capped at midnight. `Item.defaultPlanMinutes` suggests a length from the item's duration goal.
- `Reminder` (`@Model`): `kind` (`ReminderKind`: morning / evening / custom), `label` (custom only), `hour`, `minute`, `weekdays` (Calendar numbers, 1 = Sunday), `isEnabled`, `createdAt`. `Reminder.seedDefaults` adds the morning (8:00 AM) and evening (8:00 PM) alerts, both off, if missing. Computed: `displayTitle`, `summary`, `daysText`.
- `TrackingType.swift`: `TrackingType` (binary/quantity), `BinarySubtype` (didIt/avoidedIt/stateCheck), `QuantitySubtype` (amount/duration/timeTarget), `QuantityDirection` (cap/target), `ToleranceMode` (absolute/percent), `TrackingMethod` (check/number/timer/nfc; `options(for:quantitySubtype:)`; its `systemImage` is now unused), `QuantityUnit`, `TimeDirection` (either / noLaterThan / noEarlierThan: for time targets, whether early, late or either side counts as on time).

## Status and Period Logic
- `Target.periods()` returns one `TargetPeriod` per cadence interval (whole window if finite, start through current if ongoing) with `result` (done / missed / open / upcoming), `loggedValue` and `settledOn`. Built in a single pass over logs sorted by counting date.
- **Rolling targets** (`isRolling == true`, `buildRollingPeriods`): one period per day, each judged by `isSatisfied` on the logs of the `intervalDays` days ending that day (two-cursor sweep over sorted logs). Current day: done while covered, open (due) once not (caps: open while under, missed once over). Past day: done if covered, else missed; skipped day (`skippedOn`) = missed unless covered. During the first `intervalDays - 1` days an uncovered past day returns `.upcoming` (no verdict; streaks and completion skip it). `settledOn` = that day; `loggedValue` = the window's sum. Not meant for time targets (the form hides the toggle). Consequences: streak and completion count days, not windows; target-page period rows and Calendar show one entry per day; `doneThisWeek()` (recentPeriods(8)) counts covered days. Quick update and the alerts need no rolling-specific code (today's period is done while covered, open when due); `homeTile` shows a covered rolling target as light blue, not green.
- `Target.recentPeriods(n)` builds only the last n started periods; use it where only the latest few matter (status, card dots, Quick update).
- Done rules: binary = any log; amount/duration = logs summed within tolerance (at least the goal for `.target`, at most for `.cap`); time target = latest log within ± tolerance minutes using the short way around the clock. Logs with no value count as met (a cap is never broken by them). A cap stays open until its period ends.
- **Evening time goals** (goal at or after noon, like a bedtime): a log with a clock time before noon counts toward the previous day's period (`countingDate(of:)`); `isEveningTimeGoal`.
- `settledOn`: the day the period's outcome was fixed: goal first met, cap first broken, or the last day if missed / a cap held. Nil while open.
- **Skipped periods**: a non-cap, unmet, started period containing a `skippedOn` date is `.missed` right away (even while current), with `settledOn` = the skip day. Logs win: if the logs meet the goal anyway, the period is `.done`. Caps ignore skips. `needsQuickLog()` returns false for a current `.missed` period (only a skip causes that for non-caps), so Quick update and the alerts drop it for the rest of the period. `status()` reads it as overdue; the Home tile is red.
- `Target.status()` (done / due / overdue) reads only the current period (`recentPeriods(1)`): done if it's met, upcoming, or a cap that hasn't been broken; due if it's open (non-cap); overdue only when a cap has already been broken this period. A missed earlier period never changes the color; it only shows in the history dots. Since 2026-11-21 the area page card tints, the item page and Home all read `homeTile()` (the pager dots and Home tint via `homeStatus`); `status()` no longer drives the cards or the item page.
- `AreaStatus.swift`: `active(in:)`, `overallStatus` (green when every target is done, yellow when any is still open; never red, since a broken cap is a today-only fact), `Optional<TargetStatus>.color`, and `Color.goalMet` / `Color.goalMissed` / `Color.setAside` (the dark green for "goal met", the dark red for a miss and the blue for set aside / Later, used on every screen; Home's tiles, status tints, dots, bars and the Calendar all read them).
- `TargetStats.swift`: `TargetStats(periods:)` gives done / missed counts, `currentStreak`, `longestStreak` and `completionRate`. Streak = consecutive `.done` periods; a missed period (or a broken cap) ends it; the open current period neither extends nor ends it; upcoming periods are ignored. Completion = done / (done + missed). Streaks count cadence intervals (`Target.streakText`: days / weeks / periods). `[Target]` helpers feed History: `bestCurrentStreak()` (active targets), `bestLongestStreak()`, `doneThisWeek()` (periods settled done in the current calendar week, from `recentPeriods(8)`).

## Alerts (Notifications)
- **Settings → Alerts** (`AlertsView`): the two built-ins (Start of day, End of day) and any number of custom reminders. A Plan alerts switch (with limit warnings) sits between them. Each has an on/off toggle; tapping opens `ReminderEditView` (time, days of the week, label for custom). The last remaining day can't be turned off. New custom reminders start on.
- **Scheduling** (`ReminderScheduler.refresh`): clears every pending request it made (ids start with `reminder.`) and rebuilds from the saved reminders.
  - Morning and custom: one repeating weekly request per enabled weekday. Morning text: "Today's focus" / "Open the app to see what's on today." (generic on purpose, so it's never stale). Custom: the label as the title.
  - Evening: a rolling window of one-off requests for the next 5 days (`alertWindowDays`) ("End of day" / "Anything left to track today?"). Today's is skipped if the time has passed or nothing is left to log (`needsQuickLog`); later days are added as long as any target is active and get re-checked on the next refresh. If nothing is left, an already-delivered end-of-day notification is cleared too.
- **Plan alerts** (Settings → Alerts → Plan alerts switch; `planAlertsEnabled` in UserDefaults, off by default): `planRequests` builds one alert per planned slot per day in the `alertWindowDays` window at its start time (weekly slots on their weekday, one-offs on their date; archived items skipped). Today's is skipped unless the item `needsQuickLog`; later days only need an active target that isn't a cap or NFC, and are re-checked on every rebuild. Added after the other alerts and trimmed soonest-first to stay within `pendingBudget` (60 of iOS's 64). `AlertCapacity.shared` (observable) records `scheduled`, `droppedPlan` and `failed` (requests iOS refused, no longer swallowed) after each rebuild; AlertsView shows an orange warning when anything is left out or refused, or the other alerts alone exceed 64, and a yellow note at 50 or more of 60 while plan alerts are on; PlanView shows a one-line orange note when `droppedPlan` > 0.
- **When it rebuilds**: launch and every return to the foreground; whenever the active targets, the set of targets left to log, or the planned slots change (a signature watched in `ContentView`, so logging, undoing, archiving, adding a target or editing a slot needs no extra calls); a significant time change (midnight/time zone) while the app is open; and edits in the Alerts screens (immediately for toggles/add/delete, after a short pause for typing or the time picker, and when leaving an edit screen).
- **Permission**: requested the first time a reminder is on and iOS hasn't been asked; if denied, the Alerts screen shows a note with an "Open iOS Settings" button.
- **App icon badge** ("Badge until done", per target via `Target.badgeNudge`, toggle in the target form's Quick update section): `Target.needsBadge()` (in `TargetQuickLog.swift`) = flagged and `needsQuickUpdate(ignoringShowTime: true)`, so logging, Skip and Not today / Later clear it and the show-from time is ignored (badge is there from the start of the day). `ReminderScheduler.refresh` sets today's count directly with `setBadgeCount` and adds silent badge-only notifications (`reminder.badge.<date>`, no title/body/sound, 12:01 AM, next `alertWindowDays - 1` days, counts assume nothing logged yet; they count toward the 60 budget before plan alerts) so the badge appears on a new day with the app closed. Permission now includes `.badge`; someone already authorized for alert/sound may need to turn Badges on in iOS Settings. `ContentView`'s scheduling signature includes the flagged set and badge count, and that refresh passes `requestingPermission: true` (launch / foreground refreshes still don't prompt).
- **Tapping an alert**: `NotificationRouter` (shared, held statically since iOS keeps only a weak delegate) sets a flag for morning/evening alerts. `ContentView` sees it once the app is active (`openQuickUpdateIfRequested`), switches to Home, clears Home's pushed screens and opens the Quick update sheet after a 0.4 s pause. `didReceive` must stay `@MainActor`: as `nonisolated` it ran off the main thread and tapping any alert crashed the app (SIGABRT in UIKit's snapshot work). Custom and plan alerts just open the app. No banners are shown while the app is open.
- **Limits**: the evening and plan alerts stop after 5 days without opening the app (`alertWindowDays`; morning/custom keep going). If another sheet is already open when an alert is tapped, the tap just opens the app. 64 pending-notification cap: the scheduler stays within 60 (`pendingBudget`), and plan alerts, added last, are the ones trimmed. Free Apple ID builds expiring also stops alerts.

Day tints are solid dark colors with a readable day number (`DayState.textColor`): dark green = all done, dark red = all missed, yellow = open or mixed, gray = future. A one-day period colors its day; a longer period colors only the day it was settled (and its last day while open). Filtered periods are computed once per update and shared.
- `PlanView` (the Weekly Plan, in the Calendar tab): one selected date (`selectedDate`) shows that day's slots on a 24-hour timeline (scrolls to about 5 AM). A strip shows that date's week with day numbers (tap to pick), arrows step one day (past days allowed, so weekly slots also appear on past days), and a Today button shows when off today. An orange note shows under the clash warning when plan alerts are being dropped (see Alerts).
- `HistoryView`: three summary cards from real data (Current streak = longest running streak of any active target, with its item name; Done this week; Longest streak = best ever of any target, with its item name; "—" when there are no targets) and the locked badge grid (static placeholder).

## Home Tiles
- `Target.homeTile(asOf:capHeldMinutes:)` (in `HomeTiles.swift`) gives each active target a `TileGroup` color and a `needsAttention` flag. It reads the same current period as `status()`, but Home and the pager dots use `homeStatus`, built from the squares; the area page's target cards and the item page read `homeTile()` too (tinted with `TileGroup.base` at 20%, labeled with `TileGroup.title`), so they agree with Home.
- Colors (`TileGroup`), sorted in this order on the card: red (a skipped period, X in Quick update; cap broken, or a time target logged outside its window; for a period longer than a day, only on its last day), yellow (needed and not met; an amount/duration target with some logged gets a dark green fill from the bottom, by fraction of its goal; also a cap with nothing logged today), green (met, or a cap logged today and still under its limit; solid dark green = fully filled), blue (set aside with Not today; a set-aside amount/duration target with progress keeps its fill), light blue (not needed until later; with progress it keeps the fill), gray (the period hasn't started). Squares are light tints (yellow/light blue/gray); green (`Color.goalMet`), red (`Color.goalMissed`) and blue (`Color.setAside`, same as the Later button) are the solid dark colors. There is no light green any more.
- Caps: red once broken; blue if set aside with Not today; yellow until something is logged today (the same once-a-day rule Quick update uses); then green. The cap-held time (`HomeSettings.capHeldMinutesKey`, Settings -> Home) no longer changes the color.
- Area tint (`homeStatus`, also used by the pager dots): yellow if any square is yellow (something left to do), otherwise red if any square is red (nothing left to do, but a miss or a broken cap), otherwise green; gray with no targets. Yellow wins over red so a to-do is never hidden by an outcome. `HomeTile.needsAttention` is now only used for the card's accessibility label.
- Long cadence (`intervalDays` > 2): light blue until planned today (an item `PlanEntry`, weekly or one-off), or 2 or fewer days left in the period; with progress it is light blue with a dark green fill while not needed yet, or yellow with a dark green fill once needed. The area tint is built from the squares (see Area tint above), so it can't contradict them (`HomeTile.progress` / `PlacedTile.progress` carry the fill; merged circles lose it). Time targets have no partial state (yellow until met, red once a log misses the window).
- Layout (`HomeTileLayout.place`): 4x3 = 12 slots. Up to 12 targets, one square each. Over 12, whole color groups merge into circles with a count, settled first (green, gray, light blue, blue, then yellow, red). A group of 5 or more becomes a big 2x2 circle (max two per card, placed at the bottom two blocks); anything else merges to a one-slot circle. Squares fill the remaining slots from the top in color order.

## Configuration & Environment
- No `.env` or secrets. Local SwiftData storage, `isStoredInMemoryOnly: false`. No CloudKit yet. Free Apple ID builds expire after 7 days (re-run from Xcode to renew; keeps data).
- The bundle identifier is still `com.duncanbagley.FirstApp` (kept on purpose after the rename so on-device data and the notification permission carry over; changing it makes iOS treat it as a new app). Target, scheme and app name are Ferb.
- Schema changes that add defaulted fields (or a whole new model, like `Reminder`) migrate automatically. **Exception:** a new non-optional enum field with a default (like `TimeDirection` was) is not filled in on existing rows and crashes when read ("Could not cast value of type Optional<Any> to …"; it happened on the phone, not in the simulator, which has no old rows). Store such fields as optional with a computed wrapper (`timeDirectionStored` + `timeDirection`; `@Attribute(originalName:)` keeps old values). New optional fields (like `PlanEntry.date`) are safe. Changes like turning a field into a different type require deleting the app (this happened once: Subarea enum -> model). The container creation `fatalError`s if migration fails.
- Build setting: default actor isolation is MainActor (Swift 5 mode). Plain types used off the main actor are marked `nonisolated` to avoid Swift 6 isolation warnings (`LogInputKind`, the app's `FerbTimerAttributes` and its `ContentState`, `PeriodResult`); apply the same to any other plain enum that warns on `==`.
- **Live Activity setup**: the Ferb target's Info needs `Supports Live Activities` (`NSSupportsLiveActivities`) = YES. The widget extension target is `FerbTimerWidget` (iOS 17, bundle ID `com.duncanbagley.FirstApp.FerbTimerWidget`) and has its own signing. Live Activities also need to be allowed for Ferb in iOS Settings (on by default). The calendar permission string (full calendar access, needed to read events) is in the Ferb target's Info.

## Notable Patterns / Conventions
- **Items are definitions, targets are actions**: cadence, logs and status live on `Target`.
- **Everything is derived from logs**: status, periods, settled days, calendar colors. Nothing is cached or stored.
- **Create and delete logs only through `target.record` / `target.remove`.**
- **One logging path**: Quick update and Log now both use `TargetLogInputs` + `LogDraft`; "still needs logging" is only defined in `needsQuickLog` (Quick update adds caps via `needsQuickUpdate`).
- **Notifications are rebuilt, not patched**: always clear-and-re-add from saved settings.
- **Archived** = hidden everywhere (counts, grid, calendar, pickers) but kept; `isActive` returns false for hidden targets, so most screens exclude them automatically.
- **Filtering happens in Swift, not SwiftData predicates** (`@Query` fetches, small data), except the archived pickers.
- **Edit rules protect history**: frequency, start and goal can't change once a target has logs.
- Proposals before changes: Duncan wants one change at a time with pros and cons explained first.
- **Live Activity**: `FerbTimerAttributes` exists twice (widget file and `TimerActivityAttributes.swift`); the type name, property names and types must stay identical or the banner silently stops working, so change both together. Only one timer banner shows at a time (starting or resuming replaces another's); pausing updates only its own banner. The key linking a target to its banner is the base64 of its JSON-encoded `persistentModelID` with sorted keys (unsorted keys made pause fail to find the banner). iOS ends a Live Activity after roughly 12 hours; the next resume starts a new one. No pause/resume buttons on the lock screen yet (that would need App Intents).
- **Delete all data keeps a hand-written model list**: when adding a model, add it to the schema and to `deleteAllData()`.
- **Delegate callbacks that touch UIKit/UI state stay on the main actor**: default isolation is MainActor, so don't mark notification-delegate methods `nonisolated`; iOS finishes the tap on the calling thread and UIKit asserts the main thread.
